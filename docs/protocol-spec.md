# Ember Protocol Specification, version 1 (drop format)

**Status:** Draft v1, written in milestone M1. Implemented and corrected in M2 and M3.
**Scope:** The one-time encrypted drop: key handling, ciphertext layout, link format, passphrase wrapping, server storage API and expiry rules. Threads (the short 1:1 conversation) are only reserved here and specified in milestone M7. Proof-of-work is specified in M4.
**Rule for implementers:** use audited libraries only (libsodium primitives or a libsodium-compatible Rust crate). Never invent primitives. If this document and a test vector disagree, stop and record the conflict in the Handoff Log.

Keywords MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

---

## 1. Goals and non-goals

**Goals**
- The server stores only ciphertext and never receives the content key, the link fragment, or the passphrase.
- Any recipient with the full link (and the passphrase, if set) can decrypt; nobody else can.
- Tampering, truncation, reordering or replacement of ciphertext is detected.
- Uploads resume after a network drop; downloads resume inside a claim window.
- Expiry (12 hours maximum) and burn-after-view are enforced by the server, and shown honestly to users.

**Non-goals (stated openly to users)**
- Preventing a recipient from keeping a copy (screenshot, camera, saved file).
- Preventing a modified client from ignoring expiry.
- Hiding network-level metadata from the server operator (see `privacy-and-logging.md`).
- Hiding file size exactly (padding only reduces precision, section 6).

---

## 2. Primitives

All primitives come from libsodium (or a compatible implementation that passes the test vectors).

| Purpose | Primitive | Key | Nonce / header | Tag / overhead |
|---|---|---|---|---|
| File content | `crypto_secretstream_xchacha20poly1305` | 32 bytes | 24-byte stream header (random, generated by init) | `ABYTES` = 17 per message (1 tag byte inside the ciphertext plus a 16-byte MAC) |
| Passphrase to key | `crypto_pwhash` with Argon2id v1.3 | output 32 bytes | 16-byte salt | n/a |
| Key wrapping | `crypto_aead_xchacha20poly1305_ietf` | 32 bytes | 24-byte random nonce | 16-byte tag |
| Sub-key derivation | `crypto_kdf_derive_from_key` (BLAKE2b) | 32-byte master | context + sub-key id | 32-byte sub-keys |
| Randomness | OS CSPRNG (`randombytes_buf` or `getrandom`) | n/a | n/a | n/a |

Constants:

```
KDF_CONTEXT   = "EMBERv1_"      (exactly 8 ASCII bytes)
AD_DROP       = "ember-drop-v1" (ASCII, additional data for every stream message)
AD_WRAP_PREFIX = the first 23 bytes of the link payload (section 5.2)
```

---

## 3. Keys

1. The sender generates a random 32-byte link secret **K** with the OS CSPRNG.
2. Sub-keys are derived with `crypto_kdf_derive_from_key(32, id, "EMBERv1_", K)`:

| id | Use |
|---|---|
| 1 | Content key for the drop stream (`K_content`) |
| 2 | Reserved |
| 3 | Thread pre-shared key (`K_psk`, milestone M7 / ADR 0008) |
| 4 | Reserved |

3. K MUST NOT be sent to the server, logged, or put anywhere other than the link fragment (or its passphrase-wrapped form).
4. Implementations MUST zeroise K, sub-keys, the passphrase and derived keys in memory as soon as practical.

---

## 4. Plaintext layout, padding and chunking

The encrypted stream is a single libsodium secretstream. Its plaintext messages are, in order:

### 4.1 Message 0: metadata record

- Exactly **4096 bytes** of plaintext, stream tag `MESSAGE`.
- Layout: `u32 big-endian json_len` ‖ `json (UTF-8)` ‖ zero padding up to 4096 bytes. `json_len` MUST be at most 4092.
- JSON object, all fields required unless marked optional:

| Field | Type | Meaning |
|---|---|---|
| `v` | integer | Metadata version, `1` |
| `kind` | string | `"file"` or `"text"` |
| `name` | string | Original file name (UTF-8, at most 255 bytes); empty string for text |
| `mime` | string | Declared media type, at most 127 bytes; informational only |
| `size` | integer | True plaintext size in bytes of the content, before padding |
| `burn` | boolean | Sender's intent: burn after first completed view |
| `created` | integer | Unix seconds when the drop was created (sender clock, informational) |
| `expires` | integer | Unix seconds when the sender expects expiry (informational; the server is the authority) |

The file name and media type exist ONLY here, inside the ciphertext.

### 4.2 Messages 1..n: content chunks

- The content (file bytes, or the UTF-8 text) is followed by zero bytes up to `padded_len` (section 6), then cut into chunks of **1,048,576 bytes** (1 MiB). All chunks except the last are exactly 1 MiB; the last holds the remainder (at least 4096 bytes, at most 1 MiB).
- Every content chunk except the last has tag `MESSAGE`. The last has tag `FINAL`.
- Every message (including message 0) is encrypted with additional data `AD_DROP`.

### 4.3 Receiver checks

A receiver MUST:
1. Decrypt messages strictly in order.
2. Fail if any message fails authentication.
3. Fail if the stream ends without a `FINAL` tag, or if bytes follow the `FINAL` message.
4. Fail if `size` exceeds 1 GiB (hard receiver limit, checked before any length arithmetic or allocation), or is greater than the decrypted padded content length, or if any padding byte after `size` is non-zero.
5. Treat `name` and `mime` as untrusted: strip path separators and control characters, limit length, never use them to choose an executable action.
6. Write plaintext to a temporary location and expose it to the user only after the `FINAL` tag verifies. Partial plaintext MUST NOT be opened or shared by default.

## 5. Ciphertext layout and link format

### 5.1 Ciphertext (what the server stores)

```
stream_header (24 bytes)
‖ msg0_ciphertext (4096 + 17 = 4113 bytes)
‖ content_chunk_1_ciphertext (chunk_len + 17 bytes)
‖ ...
‖ content_chunk_n_ciphertext (FINAL)
```

**Transport parts** (for resumable upload and download). The server treats parts as opaque bytes:
- **Part 0** = `stream_header ‖ msg0_ciphertext` = **4137 bytes**.
- **Part i (i >= 1)** = the ciphertext of content chunk i, at most **1,048,593 bytes** (1 MiB + 17).

Reference numbers (padding rule of section 6):

| Content size | `padded_len` | Content chunks | Last chunk (plaintext) | Total ciphertext bytes |
|---|---|---|---|---|
| 0 | 4096 | 1 | 4096 | 8,250 |
| 4,097 | 65,536 | 1 | 65,536 | 69,690 |
| 1,048,576 | 1,048,576 | 1 | 1,048,576 | 1,052,730 |
| 1,048,577 | 1,114,112 | 2 | 65,536 | 1,118,283 |
| 52,428,800 (50 MiB, default cap) | 52,428,800 | 50 | 1,048,576 | 52,433,787 |

### 5.2 Link

```
https://<host>/d/<blobId>#<payload>
```

- `blobId`: 16 random bytes from the server, base64url without padding (22 characters). Server-generated; never derived from content.
- `payload`: base64url (RFC 4648 section 5, no padding) of the binary payload below. It lives after `#`, so browsers and apps MUST NOT send it to any server. Implementations MUST NOT log the fragment, put it in analytics, in crash reports, or in a `Referer` header.

**Payload, no passphrase** (34 bytes, 46 characters):

| Offset | Size | Field |
|---|---|---|
| 0 | 1 | `version` = `0x01` |
| 1 | 1 | `flags` (bit 0 = passphrase protected = 0; other bits MUST be 0) |
| 2 | 32 | K |

**Payload, passphrase protected** (95 bytes, 127 characters):

| Offset | Size | Field |
|---|---|---|
| 0 | 1 | `version` = `0x01` |
| 1 | 1 | `flags` (bit 0 = 1) |
| 2 | 1 | `ops` (Argon2id passes) |
| 3 | 4 | `mem_kib` (u32 big-endian, memory in KiB) |
| 7 | 16 | `salt` (random) |
| 23 | 24 | `nonce` (random) |
| 47 | 48 | `wrapped_K` (32-byte ciphertext ‖ 16-byte tag) |

Wrapping: `P = Argon2id(passphrase, salt, ops, mem_kib * 1024, out_len = 32)`; `wrapped_K = XChaCha20-Poly1305-IETF-Encrypt(key = P, nonce = nonce, ad = payload[0..23], message = K)`.

Defaults and limits: sender default `ops = 3`, `mem_kib = 65536` (64 MiB), chosen so that mid-range and low-end Android phones finish in a few seconds. Receivers MUST reject `ops` outside 1 to 10 and `mem_kib` outside 8192 to 262144 (denial-of-service guard). Parameters can be raised in a later link version.

Receivers MUST reject `http://` links unless the host is loopback or the Android emulator host (`10.0.2.2`), and MUST reject hosts containing anything other than letters, digits, `.`, `-`, `:`, `[` and `]`.

Receivers MUST reject unknown `version` values and any set unknown flag bit, with a message telling the user to update the app.

### 5.3 QR code

The QR code encodes the full link as text, error correction level M. Link length stays under about 120 characters without a passphrase and under about 200 with one, which keeps the QR code small and scannable on low-end cameras.

---

## 6. Padding

`padded_len` for content of `size` bytes:

```
if size <= 4096:  padded_len = 4096
else:             padded_len = ceil(size / 65536) * 65536
```

This hides exact size within a 64 KiB band. It is a mitigation, not a guarantee: the server still sees approximate size and timing. Metadata record (message 0) is always 4096 bytes.

## 7. Server storage API (draft v1, finalised in M3)

All endpoints are HTTPS only. No cookies, no accounts. Responses carry `Cache-Control: no-store`. Error bodies are JSON `{"error": "<code>"}`. IDs and tokens are random and unguessable.

| Method and path | Auth | Purpose |
|---|---|---|
| `GET /v1/pow/challenge` | none | Request a proof-of-work challenge. Returns `{"challenge": "<str>", "difficulty": <u32>, "expires_at": <u64>}`. |
| `POST /v1/blobs` | PoW | Create an upload. Body: `{"size": <total ciphertext bytes>, "parts": <n>, "burn": <bool>, "ttl_secs": <=43200}`. Headers: `X-Pow-Challenge`, `X-Pow-Nonce` (or optional body field `pow`). Returns `{"id", "delete_token", "expires_at", "max_part_bytes"}`. |
| `PUT /v1/blobs/{id}/parts/{n}` | `Authorization: Bearer <delete_token>` | Upload part n. Idempotent; replaces a previous upload of the same part. |
| `POST /v1/blobs/{id}/complete` | Bearer delete token | Server verifies every part exists and the total size matches; the blob becomes downloadable. |
| `GET /v1/blobs/{id}` | none | Metadata only: `{"size", "parts", "burn", "expires_at", "state"}`. No side effects. |
| `POST /v1/blobs/{id}/claim` | none | Start a download. For burn blobs: returns `{"claim", "claim_expires_at"}` (10-minute window) and rejects further claims (`409`). For other blobs: returns `{"claim": null}`. |
| `GET /v1/blobs/{id}/parts/{n}` | `X-Claim` header for burn blobs; none otherwise | Download part n. HTTP `Range` is supported inside a part. |
| `POST /v1/blobs/{id}/finish` | `X-Claim` | Receiver reports a verified full download; a burn blob is deleted immediately. |
| `DELETE /v1/blobs/{id}` | Bearer delete token | Sender deletes early. |

Rules:
- **Proof-of-Work (PoW):** SHA-256 hashcash `SHA-256(challenge || nonce_be_bytes) < 2^(256 - difficulty)`. Challenge tokens are signed statelessly with server secret and valid for 5 minutes. Solved challenges are tracked in-memory to prevent replay. Missing, expired, replayed, or invalid solutions return `400 Bad Request`.
- **Rate limiting:** Coarse per-IP in-memory sliding window counters (target 15-minute TTL). Excessive requests return `429 Too Many Requests` with `Retry-After`.
- **Delete token:** 32 random bytes. The server stores only a hash of it and compares in constant time.
- **Burn-after-view:** a plain `GET` MUST NEVER burn a blob, so link-preview bots cannot consume it. Burning happens on `finish`, or when the claim window ends without a finish, whichever is first. An unfinished claim window deletes the blob too, which is the honest meaning of "one view"; senders are told this.
- **Expiry:** `expires_at = created_at + min(ttl_secs, 43200)`. A sweeper deletes expired blobs and a lazy check refuses access after expiry. Expired and burned blobs both return `410 Gone`.
- **Part count and size must agree:** `POST /v1/blobs` is rejected unless `parts >= 2` and `4137 + (parts-1)*4113 <= size <= 4137 + (parts-1)*1,048,593` (part 0 is exactly 4137 bytes; every content part carries 4096 bytes to 1 MiB of plaintext plus 17 bytes of overhead).
- **Claims are atomic:** claim and finish operations are serialised so a burn-after-view blob can never be handed to two readers (single-instance servers use an in-process lock; multi-instance deployments need an atomic compare-and-set in the shared store).
- **Client address:** rate limits use the TCP peer address. `X-Forwarded-For` and `X-Real-IP` are honoured only when the peer is a configured trusted proxy, and the right-most untrusted entry is used.
- **Limits:** default total ciphertext cap 52,433,787 bytes (50 MiB of content); part size cap 1,048,593 bytes; configurable. Uncompleted uploads expire after 1 hour.
- **Server never parses ciphertext.** It checks sizes, counts and tokens only.
- **Web receiver headers:** strict CSP, `Referrer-Policy: no-referrer`, no third-party scripts.

## 8. Receive flow (normative summary)

1. Parse the link. Reject bad version or flags. If passphrase flag is set, ask for the passphrase and unwrap K (reject on tag failure).
2. `GET /v1/blobs/{id}` to read size, parts, burn flag and expiry. Show the user a clear warning if `burn` is true ("this can be opened once").
3. Get explicit user confirmation, then `POST .../claim`.
4. Download parts in order, decrypting as they arrive, writing to temporary storage.
5. Verify the `FINAL` tag and the checks in section 4.3.
6. `POST .../finish`, then expose the file or text to the user.

- Link `version` byte 1 and metadata `v` 1 describe this document.
- Any change to primitives, sizes, KDF contexts or layout requires a new version byte and updated test vectors.
- Thread messages (M7) will use sub-key id 3 and a separate section of this document.

## 11. Implementation checklist (for M2 and M3 agents)

- [ ] K from CSPRNG; sub-keys via KDF with the exact context
- [ ] Metadata record exactly 4096 bytes, validated on read
- [ ] Padding rule and zero-padding verification
- [ ] Chunking at 1 MiB, `FINAL` tag on the last chunk only
- [ ] Parts 0..n match section 5.1 byte-for-byte
- [ ] Link build and parse, strict flag and version checks
- [ ] Passphrase wrap and unwrap with parameter bounds
- [ ] Zeroisation of secrets
- [ ] Server never receives K, the fragment, or the passphrase (asserted in tests)
- [ ] Burn-after-view survives a bot-style `GET`, and burns on `finish` or claim expiry
- [ ] All vectors in section 10 pass, including negative cases

## 12. Ephemeral 1:1 Threads and Mailboxes (ADR 0008)

Milestone M7 introduces optional short-lived 1:1 encrypted threads associated with drops.

### 12.1 Handshake: Noise Pattern `Noise_NNpsk2_25519_ChaChaPoly_BLAKE2s`

1. **Pre-Shared Key (`K_psk`):**
   Derived directly from master drop key $K$ using sub-key ID 3:
   $$K_{\text{psk}} = \text{crypto\_kdf\_derive\_from\_key}(32, 3, \text{"EMBERv1\_"}, K)$$
2. **Handshake Sequence:**
   ```text
   -> e
   <- e, ee, psk
   ```
   Both peers generate ephemeral X25519 keypairs ($e_A, e_B$). No persistent identities or static keys are used.
3. **Handshake Wire Format:**
   Both messages are prepended with a 1-byte version header `0x02`:
   - Initiator message (Part 1): `[0x02, ..noise_msg1]` (49 bytes).
   - Responder message (Part 2): `[0x02, ..noise_msg2]` (49 bytes).
   Messages lacking `0x02` or differing in length MUST be rejected cleanly.

### 12.2 Directional & Rendezvous Mailbox Capabilities

#### Rendezvous Mailbox
Derived deterministically from master drop key $K$ using sub-key ID 8 (`SUBKEY_ID_THREAD_RENDEZVOUS`):
$$\text{seed}_{\text{rendezvous}} = \text{crypto\_kdf\_derive\_from\_key}(32, 8, \text{"EMBERv1\_"}, K)$$
Sub-keys derived from $\text{seed}_{\text{rendezvous}}$:
- `SUBKEY_ID_RENDEZVOUS_ID = 1`: Mailbox identifier (first 16 bytes base64url-encoded).
- `SUBKEY_ID_RENDEZVOUS_PUSH = 2`: Push capability token (32 bytes base64url-encoded).
- `SUBKEY_ID_RENDEZVOUS_PULL = 3`: Pull capability token (32 bytes base64url-encoded).

> [!WARNING]
> Any holder of the drop link possesses $K$ and can derive the rendezvous mailbox capability to read or delete rendezvous messages.

#### Directional Session Mailboxes
Upon handshake completion, both peers obtain identical 32-byte handshake hash $h$:
$$h = \text{handshake.get\_handshake\_hash}()$$
Directional mailbox seed is derived via KDF with sub-key ID 6 (`SUBKEY_ID_THREAD_MAILBOX`):
$$\text{seed}_{\text{session}} = \text{crypto\_kdf\_derive\_from\_key}(32, 6, \text{"EMBERv1\_"}, h)$$

Sub-keys derived from $\text{seed}_{\text{session}}$:
| Constant | Subkey ID | Purpose |
|---|---|---|
| `SUBKEY_ID_MAILBOX1_ID` | 10 | Mailbox 1 (Init $\to$ Resp) ID |
| `SUBKEY_ID_MAILBOX1_PUSH` | 11 | Mailbox 1 (Init $\to$ Resp) Push token |
| `SUBKEY_ID_MAILBOX1_PULL` | 12 | Mailbox 1 (Init $\to$ Resp) Pull token |
| `SUBKEY_ID_MAILBOX2_ID` | 20 | Mailbox 2 (Resp $\to$ Init) ID |
| `SUBKEY_ID_MAILBOX2_PUSH` | 21 | Mailbox 2 (Resp $\to$ Init) Push token |
| `SUBKEY_ID_MAILBOX2_PULL` | 22 | Mailbox 2 (Resp $\to$ Init) Pull token |

- `mailbox_init_to_resp`: Initiator pushes, responder pulls.
- `mailbox_resp_to_init`: Responder pushes, initiator pulls.

### 12.3 Relay Mailbox API & Proof-of-Work

Mailbox creation via `POST /v1/mailboxes` requires a valid Proof-of-Work solution, reusing the M4 challenge mechanism (`body.pow` or `X-Pow-Challenge`/`X-Pow-Nonce` headers). Mailboxes expire after 12 hours (`MAX_LIFETIME_SECS = 43200`).

### 12.4 Session-Level Transport Encryption

Messages are encrypted using `snow::StatelessTransportState` (RFC 7539 ChaCha20-Poly1305):
- 64-bit sequence counter `seq` maps to the 96-bit nonce.
- **Binary Wire Envelope (Version 3):**
  `v(1 byte = 0x03) | seq(8 bytes, big-endian) | ciphertext(variable)`
  - Header is exactly 9 bytes (`THREAD_MSG_HEADER_LEN = 9`).
  - Minimum envelope length is 25 bytes (9 bytes header + 16 bytes Poly1305 MAC tag).
  - Receivers strictly verify `v == 3`; obsolete versions (`v = 1`, `v = 2`) or truncated envelopes are rejected cleanly.
- **Size Limits & Memory Safety:**
  - Message text is capped at 4096 bytes (`MAX_THREAD_TEXT_BYTES = 4096`).
  - Total plaintext JSON is capped at 4608 bytes (`MAX_THREAD_MSG_BYTES = 4608`).
  - Ciphertext is capped at 4624 bytes (`MAX_THREAD_CIPHERTEXT_BYTES = 4624`). Receivers validate ciphertext length before allocating memory buffers. Payloads exceeding this limit (such as raw 65535-byte Noise packets) are rejected before buffer allocation.
- **Sequence Number Acceptance Policy:**
  - Receivers accept sequence numbers `seq >= expected_seq`. Upon successful authentication and decryption, expected sequence number advances to `seq + 1`. This allows forward progress despite dropped messages.
  - Receivers strictly reject sequence numbers `seq < expected_seq` as replay attacks.
  - Tampered or corrupted ciphertexts that fail Poly1305 MAC verification do NOT advance the sequence counter.
  - A guard enforces `seq < u64::MAX`; if sequence reaches `u64::MAX`, encryption halts with `EmberError::SeqOverflow`.
- **Inner Message Integrity:**
  - Inner JSON `ThreadMessage.seq` MUST match the outer binary envelope `seq`.
  - Inner `ThreadMessage.sender_handle` MUST validate against the handle format `^[a-z]+-[a-z]+-\d{4}$`.
- **Authentication & Concurrency:**
  - In Noise `NNpsk2`, the initiator is authenticated to the responder by the first valid transport message.
  - Multiple initiators: If multiple parties scan the same QR code / drop link, each attempts a handshake on the rendezvous mailbox. The responder accepts the first valid handshake message; subsequent or racing attempts fail or are ignored.
- **Traffic Analysis Limitation:**
  - Thread messages are NOT padded to fixed length. Ciphertext lengths leak approximate message size to relay observers.

> [!NOTE]
> Thread forward secrecy is not to be marketed until an independent cryptographer has reviewed the integration during external audit.
